## Что это за срез

Это **фрагменты реальных файлов** рабочего проекта, собранные в одну папку. Не самостоятельное приложение: не собирается и не запускается.

Что сознательно оставлено как есть:
- **импорты не тронуты.** `from db.models.tour import ...`, `from services.router_service
  import RouterService`, `from settings import TYPE_POINT_CMS` - в проекте эти пути
  существуют. Здесь они специально не «починены» по ним видно
- **сеанс БД приходит извне** (FastAPI-dependency, один на запрос). Жизненный цикл
  `session` в срезе не показан - коммит и откат делает `managed_transaction`
- **`main.py`** - фрагмент главного `main.py` приложения: тут только регистрация
  хэндлера `CollectionGroupNotFoundError 404`
- **`common.py`** - в проекте `services/collection_group/utils/common.py`;
  здесь лежит плоским файлом для читаемости
- **тестов, миграций, `__init__.py`, зависимостей** в срезе нет.

## Что такое группа коллекций

`collection_group` — это **надстройка над коллекциями** раздел, которым
коллекции группируются внутри компании. Одна группа объединяет много коллекций
коллекция принадлежит **никому или одной** группе.

## Задача

Нужны были «группы» для коллекций - чтобы в CMS коллекции можно было
раскладывать по разделам

**Новая сущность `collection_group`:**
`id`, `company_id`, `image` (ресайз до 512 по длинной стороне, пропорции
сохраняются), локализованные `name` (≤128) и `description` (≤512)

**Связь с коллекциями:**
в `collection_realm` добавили `group_id` - `NULL` по умолчанию, FK на
`collection_group.id`. Опционально: коллекция может жить без группы

**Новые API** - CRUD групп + два пакетных:
`all`, `create`, `update`, `delete`, `update_list`, `update_order`
`update_list` - пачкой переназначает коллекции группы: на вход два массива
`new_collections` / `delete_collections`, на выходе те же два массива
`update_order` - ручная сортировка групп внутри компании

## Место модуля в проекте

Продукт - CMS для VR-туров: контент-менеджеры отелей собирают туры из
связанных сущностей (коллекции, сферы, хотпоинты) Отдельно - админка платформы с другой
ролью и другим набором прав

`collection_group` - один из модулей. Сложность здесь не
в самом CRUD, а в связях: группа - коллекции, файлы в хранилище,
изоляция по компании и роли с разным доступом

## Структура

Восемь файлов. Читать лучше в таком порядке

| # | Файл | Роль |
|---|---|---|
| 1 | `schemas.py` | данные, запросы, ответы |
| 2 | `api_collection_groups.py` | что умеет модуль 6 роутов |
| 3 | `service.py` | транзакция, DTO |
| 4 | `repository.py` | единственное место с запросами |
| 5 | `common.py` | два хелпера транзакция и удаление файла |
| 6 | `dependencies.py` | доступ к компании + распаковка `data` |
| 7 | `description_api.py` | тексты и примеры для Swagger |
| 8 | `main.py` | хэндлер `NotFound 404` |

### 1. `schemas.py`
Pydantic-модели: запросы (`...CreateRequest`, `...UpdateRequest`,
`...UpdateOrderRequest`), внутренние DTO для обмена сервис - роутер и
ответы API (`Coll*`) логики нет вообще

### 2. `api_collection_groups.py`
Поинты, `Depends`, `UploadFile`, коды ответов. Место, где известно и «до коммита»,
и «после коммита»: загрузка в `try`, удаление нового файла в `except`,
удаление старого - после успешного ответа сервиса

### 3. `service.py`
Открывает и закрывает транзакцию, кидает
`CollectionGroupNotFoundError`, превращает ORM-модель в DTO. Каждый метод
читается как последовательность шагов

### 4. `repository.py`
Единственный файл с запросами. Отдаёт ORM-объекты и маленькие result-классы
(вроде `old_image`) - потому что вызывающему нужно старое значение **после**
коммита, а брать его вторым запросом не хочется Здесь же `case()` +
`RETURNING` в `update_order` - один запрос вместо N

### 5. `common.py`
Два хелпера:
- `managed_transaction` - иначе `try/commit/rollback` копипастится в каждый
  метод сервиса и однажды разъедется;
- `delete_file_by_url` - **не** пробрасывает ошибку наверх успешный коммит
  не должен превращаться в 500 из-за ошибки хранилища ошибка идёт
  в лог как `WARNING`

### 6. `dependencies.py`
Превращает `data: str` в pydantic-модель и проверяет доступ к компании -
**до** тела эндпоинта

### 7. `description_api.py`
Класс `ApiExampleCollectionGroup` с текстами и JSON-примерами для Swagger

### 8. `main.py`
`CollectionGroupNotFoundError - 404`

## Почему данные в `data` строкой

Формат согласован с фронтом: **в запросе есть файл**
(`image`), а файл в JSON-тело не положить. В multipart вложенный объект
тоже не передать - только строки. Договорились, что сложный payload
сериализуется на клиенте в JSON и едет строкой в поле `data`

Два запроса (сначала upload, потом create
с URL) - ручная склейка состояния на клиенте
и окно, где файл уже загружен, а сущности ещё нет. Одним запросом проще
и им, и мне, если запись не удалась, роутер удаляет файл

Как это выглядит в коде:
data: str = Form(..., description=ApiExampleCollectionGroup.create_group)
image: UploadFile | None = None

Минус этого решения: в Swagger нет структуры
payload. Swagger показывает data как один текстовый инпут, а не как
набор полей с типами Field(examples=...) в моделях в доку не попадает запрос не выводится. Единственное, что видит
клиент description поля data, поэтому описания из description_api.py -
не украшение, а фактический контракт
